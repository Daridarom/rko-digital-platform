# Архитектура RKO Digital Platform

## Принципы

- `cosmatica.org` остаётся каноническим источником публичных материалов.
- Интерфейсы платформы индексируют и представляют материалы, не создавая вторую независимую файловую библиотеку.
- Google Drive может использоваться как внутренний архив и источник рабочего контекста, но публичные ссылки ведут на РКО.
- Модули должны уметь существовать независимо и постепенно объединяться общей навигацией, поиском и связями.
- Публичная витрина и внутренний аналитический реестр не должны смешиваться: внутренний слой может быть существенно богаче публичной карточки.
- Исторические данные не удаляются только потому, что карточка скрыта из основной выдачи.

## Модель библиотеки

Каждая запись содержит: `title`, `author`, `year`, `pages`, `category`, `level`, `annotation`, `format`, `size`, `rko_url`, `cover_url`.

## Модель проектов

По обновлению требований от 16.09.2026 раздел проектов рассматривается как отдельный структурированный слой платформы.

Для каждого проекта нужна стабильная запись, содержащая как минимум:

- идентификацию и статус;
- замысел и фактически подтверждённый ход;
- территорию и участников;
- связь с НС-2117;
- то, что проект формирует;
- предшественника и наследника / следующий этап;
- подтверждённый след;
- связи для целевого сетения.

Полная рабочая анкета: `design/coevolution-2026/PROJECT_PASSPORT.md`.

Требования к обновлению раздела Cosmatica: `design/cosmatica-2026/NS2117_PROJECT_MODEL.md`.

### Публичный слой

Пользователь видит понятное описание: смысл, статус, территория, связь с НС-2117, что формируется, куда идёт проект, подтверждённый след, связанные проекты и действие для участия.

### Внутренний слой

Реестр может хранить источники, предшественников и наследников, повторяемость, устойчивые формы, пять сфер влияния, роль, грань, служебную зрелость, пробелы данных, запросы и предложения для сетения.

Рабочая шкала зрелости 0–3 из технического тома НС-2117 не является публичным рейтингом качества. Она используется только как внутренний индикатор состояния.

### Связи между сущностями

Минимальные типы связей:

- `predecessor`;
- `successor`;
- `part_of`;
- `includes`;
- `method_from`;
- `feeds`;
- `network_match`.

Перед переводом карточки в архив проверяется, не продолжилось ли дело в другой карточке, сезоне, отделении или устойчивой форме вне витрины.

## Версия 0.1

Клиентское статическое приложение без сервера. Для 480 записей библиотеки локальный поиск остаётся быстрым и позволяет разместить прототип на GitHub Pages.

Дизайн-прототипы `design/cosmatica-2026/` и `design/coevolution-2026/` не являются production-системой и не определяют окончательную серверную архитектуру.

## Следующий слой

Для семантического поиска потребуется серверный индекс / vector store. Его можно построить из метаданных и разрешённых для индексации текстов, сохраняя переход пользователя на исходную карточку РКО.

Для реестра проектов потребуется структурированное хранилище, поддерживающее стабильные ID, историю статусов, типизированные связи, источники и разделение публичных / внутренних полей. Конкретная база данных выбирается после согласования ТЗ и реальных шаблонов платформы.

## Синхронизация

Отдельный job должен периодически обходить `cosmatica.org/library`, обновлять метаданные, находить новые карточки и сохранять стабильные идентификаторы.

Для проектов синхронизация не должна механически копировать статус CMS. Нужна проверка фактического состояния и связей: действующая карточка может быть пустой, а реализованная — иметь живого наследника. Поэтому автоматический импорт дополняется ручной верификацией реестра.
